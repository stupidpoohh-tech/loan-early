# 조기상환 계산기

대출을 중간에 갚았을 때 **실제 순이득이 얼마이고 언제 돌아오는지** 계산하는 단일 화면 웹 도구입니다.

기존 대출계산기와 다른 점은 일부상환 후 금융사가 **기간을 줄이는지**, **월 납입액을 재산정하는지**를
구분한다는 것입니다. 같은 금액을 넣어도 이 하나로 이득이 3배 가까이 갈립니다.

답하는 질문은 셋입니다.

1. 지금 X원을 넣으면 총 얼마가 줄어드는가
2. 그 이득이 언제 돌아오는가 — 매달인가, 만기에 몰아서인가, 본전은 언제인가
3. 미루면 얼마를 잃는가

로그인·서버·분석 스크립트·광고가 없습니다. 입력값은 브라우저 밖으로 나가지 않습니다.
바깥으로 나가는 링크는 화면 맨 아래 "서비스 더보기"(잔고 캘린더) 하나뿐이고,
누르기 전에는 아무 요청도 생기지 않습니다.

## 실행

```sh
npm install
npm test        # 엔진·포맷터 60개 테스트
npm run dev
npm run build   # 타입 검사 → 테스트 → vite build. 테스트가 깨지면 배포가 막힙니다
```

`npm run build` 는 타입 검사와 테스트를 먼저 돌립니다. `dist/` 는 서버가 필요 없는 정적 산출물이고,
`base: './'` 로 빌드하므로 하위 경로나 웹뷰에서도 그대로 열립니다.

## 구조

```
src/
  loan.ts        계산 엔진 — DOM 참조 금지, 순수 함수만
  loan.test.ts   픽스처와 성질 테스트
  format.ts      원화·날짜 포맷터
  main.ts        DOM 바인딩과 렌더
  style.css
  fonts/         IBM Plex Mono (라틴 서브셋, 30KB)
index.html
```

계산은 UI와 완전히 분리되어 있습니다. `loan.ts` 는 DOM을 모르므로 프레임워크와 무관하게 테스트되고,
나중에 다른 화면 기술로 옮기더라도 그대로 따라갑니다.

프레임워크 없이 vanilla DOM을 쓴 이유는 화면이 하나이고 상태가 단순하기 때문입니다.
번들은 JS 20KB · CSS 14KB(gzip 각 8.4KB · 3.8KB)라 웹뷰로 옮기기 쉽습니다.

## 계산 규칙

원리금균등 상환을 전제로, 회차마다 이자를 먼저 떼고 나머지를 원금에서 뺍니다.
**반올림 방향이 결과를 1원 단위로 좌우하므로 규칙을 고정했습니다.**

| 대상 | 규칙 | 이유 |
|---|---|---|
| 이자 | 반올림 `round(잔액 × 월이율)` | 총이자 픽스처가 이 방향에서만 맞습니다 |
| 중도상환수수료 | 절사 `floor(상환원금 × 요율)` | 실제 청구액이라 금융사 관행대로 원 미만을 버립니다 |
| 차액 재상환분 수수료 | 반올림 | 매달 같은 금액을 넣는다는 가정 위의 추정치입니다 |
| 재산정 납입액 | 올림 후 보정 | 아래 참고 |

**순이득(net)이 이 제품의 유일한 1차 지표입니다.**

```
순이득 = 앞으로 덜 내는 총액 − (갚는 원금 + 중도상환수수료)
```

총이자 절감액·월 인하폭·본전 시점은 전부 2차 지표입니다. 화면 어디에서도 "절감액"이라는
모호한 단어를 단독으로 쓰지 않습니다. 총이자 절감인지 순이득인지, 언제 받는지가 담기지 않기 때문입니다.

### 재산정 납입액을 왜 한 번 더 보정하는가

닫힌 식 `ceil(B × i / (1 − (1+i)^−n))` 은 이자를 원 단위로 반올림하지 않는다고 보고 계산합니다.
실제로는 회차마다 최대 0.5원씩 오차가 쌓여, 마지막에 몇 원이 남아 **회차가 하나 더 붙는** 경우가
생깁니다(실측 210개 조합 중 5개). 3원을 받으려고 한 달을 더 끄는 스케줄은 존재하지 않으므로,
`fitPayment()` 가 `n` 회 안에 끝나는 최소 납입액까지 1원씩 올립니다.

## 명세와 다르게 간 곳

원 명세는 완성본이었지만, 만들면서 확인된 문제 몇 가지는 방향을 바꿨습니다.

- **수수료 반올림** — 명세는 `round` 였으나 픽스처(`P=100,000 → 985원`)는 절사여야 맞습니다.
  `round(985.5)` 는 986이 됩니다. 실제 청구액은 절사, 재상환분 추정치는 반올림으로 나눴습니다.
- **`P = 0` 처리** — 명세대로면 상환액이 0인데도 재산정 식이 돌아 원래 납입액과 몇 원 어긋나,
  아무것도 하지 않았는데 손익이 생깁니다. `P > 0` 일 때만 재산정합니다.
- **상환액 상한** — 잔액을 넘겨 입력해도 잔액까지만 씁니다. 넘는 돈에 수수료를 물릴 이유가 없습니다.
- **월 납입액을 모를 때** — 남은 회차로 역산하는 입력을 넣었습니다. 만기나 남은 회차는 알아도
  월 납입액을 정확히 모르는 경우가 흔해서, 이게 없으면 결과 화면에 닿지 못합니다.
- **정률 수수료의 부과기간 면제** — 명세는 정률(flat)을 무기한 부과로 뒀지만, 국내 가계대출은
  약관상 대부분 3년 뒤 면제라 명세 쪽이 현실과 어긋납니다. 산정방식과 무관하게 부과기간이
  지나면 0으로 계산합니다(부과기간 0 = 무기한). 이 면제가 "언제 갚을까" 축의 유일한 반전
  요소입니다 — 금리가 낮고 면제가 코앞이면 몇 달 미루는 쪽이 이기고, 그때는 화면이 먼저
  제안합니다. 그 밖에는 미루기가 늘 손해라 시점 슬라이더가 장식이 됩니다.
- **금액 입력 서식** — `30000000` 은 자릿수를 셀 수 없습니다. 쉼표를 넣으면서 캐럿 위치를
  유지합니다.
- **폰트** — 본문 폰트를 Google Fonts에서 불러오면 외부 요청이 생겨 "브라우저 안에서만 계산"이
  사실이 아니게 되고 웹뷰 이식에도 걸립니다. 숫자용 IBM Plex Mono(라틴 서브셋 30KB)만 자체
  호스팅하고, 한글 본문은 설치된 폰트 → 시스템 스택으로 내려갑니다.
- **예시 기본값** — 명세의 월 578,880원은 84회에 딱 떨어지지 않아 3천원짜리 85회차가 붙습니다.
  84회에 맞는 578,903원을 씁니다.
